# ADR 0005: Use Alembic for Database Migrations

## Status

Accepted

Supersedes the migration guidance implied by
[ADR 0001: Use Rust and Axum for the Backend](0001-rust-backend.md).
ADR 0001's Rust/Axum backend decision is no longer in effect; the backend is
implemented in Python with FastAPI. Any SQLx-style migration approach that
followed from ADR 0001 is likewise not in effect.

## Context

The Jarumba Music backend now stores its domain data in **Supabase PostgreSQL**
(the database decision is unchanged) and defines its schema as SQLAlchemy ORM
models in `services/api/app/models/`:

* `profiles`
* `favorites`
* `playlists`
* `playlist_tracks`
* `recently_played`

`profiles.id` is the same UUID as `auth.users.id` and carries a foreign key to
`auth.users`. Supabase Auth owns the `auth` schema; Jarumba must never create,
alter, or drop it.

Schema changes must be versioned, reviewable, reproducible, and reversible, and
they must be applied identically by every developer and environment. The
project already relies on SQLAlchemy 2.x for both the ORM models and the engine
created in `app/database.py`, so the ORM models are the single source of truth
for the intended schema.

At the time of this decision, no migration tool was configured: `alembic` was
not installed and the `migrations/` directory was empty. A migration mechanism
had to be selected deliberately rather than assumed.

## Options Considered

### Alembic

Alembic is the migration tool written by the author of SQLAlchemy and is the
de-facto standard for SQLAlchemy projects. It consumes `MetaData` directly,
can autogenerate revisions by diffing models against the live database, and
supports offline (`--sql`) rendering for review and manual application.

### Hand-written SQL migration files

Plain `.sql` files applied manually or by a custom script would have no
dependency on the Python stack. However, they would duplicate the schema that
already exists in the ORM models, giving the project two sources of truth that
drift silently. They would also provide no automatic diffing, no revision
graph, and no built-in downgrade path, and would require custom tooling to
track which files had been applied.

### Supabase CLI migrations

The Supabase CLI (`supabase migration new`, `supabase db push`) manages SQL
files under `supabase/migrations/`. It is excellent for the Supabase-native
features it targets — RLS policies, Edge Functions, and generated TypeScript
types — and it is the natural home for RLS policies when those are introduced.

It was not selected as the *canonical application* migration mechanism because
it is unaware of SQLAlchemy `MetaData` and cannot diff against the ORM models.
Using it for the application tables would mean hand-maintaining SQL that
mirrors the models, reintroducing exactly the two-sources-of-truth drift
problem described above. It would also place the project's schema history in a
second, independent migration log, making it ambiguous which tool owns a given
change.

This is not a rejection of the Supabase CLI outright. Supabase remains the
platform, and the CLI can be layered on later for the Supabase-specific
concerns it does own (RLS policies in particular) without replacing Alembic,
since both ultimately express changes as SQL against the same database.

## Decision

The canonical application migration mechanism for Jarumba Music is **Alembic**,
configured under `services/api/alembic/` with `services/api/alembic.ini`.

1. **Backend stack.** The backend is Python with **FastAPI**, not the Rust/Axum
   design described in ADR 0001. This supersedes ADR 0001's backend-language
   decision and the SQLx-based migration approach that followed from it.

2. **Database.** Supabase **PostgreSQL** remains the database. This decision
   changes only how schema changes are authored and applied; it does not change
   the database platform, the connection configuration, or the Supabase project.

3. **Single source of truth.** The SQLAlchemy models in `app/models/` are
   authoritative. `alembic/env.py` imports `Base.metadata` from `app.models`,
   so a revision is generated by diffing the models against the database rather
   than by hand-writing schema.

4. **Connection configuration.** The database URL is read at runtime from the
   application's existing settings (`app.config.get_settings()`, i.e. the same
   `DATABASE_URL` the API uses). It is deliberately **not** stored in
   `alembic.ini`, so the Supabase connection string is never committed and
   migrations always target the database the application actually uses.

5. **Supabase-owned objects are excluded.** `auth.users` is registered in the
   metadata as a read-only stub so the `profiles.id` foreign key resolves.
   `env.py` filters it out via `include_object`, and `include_schemas` is fixed
   to `False`. Both settings matter: the Supabase database contains `auth`,
   `storage`, `realtime`, `vault`, `graphql`, and `extensions` schemas that
   Jarumba does not own. Reflecting them would cause autogenerate to emit
   `DROP TABLE` for objects the application must never touch.

6. **Schema is verified before it is applied.** `alembic upgrade head --sql`
   renders the migration offline for review, which is how the initial revision
   was checked (it creates only Jarumba's five tables plus `alembic_version`,
   and emits no `DROP`).

### Scope of Alembic's ownership

Alembic owns exactly the five Jarumba domain tables. It does not own, and must
not manage, the `auth` schema. Row Level Security policies are a separate
concern and are intentionally **not** part of this decision; they will be
addressed in their own step.

## Consequences

### Positive

- One source of truth: the ORM models drive the schema; no hand-maintained SQL
  duplicates to drift.
- Revisions are versioned, reviewable, and applied in a deterministic order.
- Every migration has a downgrade path, so changes are reversible.
- Autogenerate turns a model change into a ready-to-review revision.
- Offline (`--sql`) rendering allows schema review without database access.
- Consistent with the existing SQLAlchemy 2.x stack; no new paradigm.
- No credentials enter version control.

### Negative

- Alembic is Postgres-specific in this configuration (the migration uses
  `gen_random_uuid()`, `now()`, and `auth.users`), so it cannot be applied to
  SQLite. Tests that need SQLite must use `Base.metadata.create_all` instead.
- Autogenerate requires a live database connection to diff against; it cannot
  run fully offline.
- `include_schemas` must stay `False` and the `include_object` filter must be
  preserved. Misconfiguring either on a Supabase project is destructive, so
  these are documented in `alembic/env.py` and `alembic/README.md`.
- Alembic is unaware of Supabase-specific objects (RLS policies, triggers owned
  by Supabase), which remain outside its management.

## Revisit Conditions

This decision may be revisited if:

- the backend is migrated to a different language or framework that requires a
  different migration toolchain;
- Supabase's CLI becomes the mandatory mechanism for the project's schema; or
- the project moves away from Supabase PostgreSQL entirely.
